# Hippocrates AI: React Frontend Development Prompts

Use the following sequence of detailed prompts to instruct your AI (Antigravity) to build the frontend. These prompts are structured to tackle the application layer by layer, ensuring the AI understands the architectural constraints, the tree-based data structures, and the required split-pane interactions.

Feed these to the AI one at a time. Do not move to the next prompt until the AI has successfully implemented and debugged the current step.

---

## Prompt 1: Project Scaffolding, Layout, and State Architecture
**Goal:** Set up the application shell, the split-pane layout, and the global state for the document tree and question queue.

**Prompt to copy/paste:**
> Act as an expert React developer. We are building the frontend for a medical study application called "Hippocrates AI". The backend is built with Django and serves document data as a flat array of blocks (nodes) that represent a hierarchical document (AST). 
> 
> Here is the initial task:
> 1. Set up a React boilerplate structure (assume Vite + TypeScript + Tailwind CSS). 
> 2. Create the main split-pane layout mimicking a wide desktop view. The layout consists of:
>    - A left sidebar (fixed width, for navigation and library).
>    - A central primary panel (the Reader View) which will eventually hold document text.
>    - A right sidebar (the Review Queue, fixed width) that holds pending question cards.
> 3. Implement global state management (use Zustand). We need a store that handles:
>    - `documentBlocks`: An array of block objects `{ id, parent_id, order, type, text }`.
>    - A selector/utility to convert this flat array into a nested tree structure for the UI.
>    - `pendingQuestions`: An array of generated question objects.
>    - `queueCount`: A derived state tracking pending questions (max limit 20).
> 
> Please write the code for the layout components and the Zustand store. Do not build the actual document text renderer or question cards yet, just the structural containers and state management.

## Prompt 2: The Recursive Document Renderer
**Goal:** Parse the flat backend array into a tree and render it dynamically.

**Prompt to copy/paste:**
> Now let's build the central Reader View. The backend sends documents as a flat adjacency list to avoid DRF nested serialization issues. 
> 
> Data model: `Block { id: string, parent_id: string | null, order: number, block_type: 'heading' | 'paragraph' | 'list_item', text: string }`
> 
> Task:
> 1. Write a React component `<DocumentRenderer>` that takes the flat array from the Zustand store and builds a parent-child map to recursively render the tree.
> 2. Create a `<BlockNode>` component that recursively renders itself and its children based on `block_type`.
> 3. Ensure every rendered DOM node includes a `data-block-id={id}` attribute. This is strictly required for our text selection and source-highlighting mechanics later.
> 4. Apply basic Tailwind typography classes to distinguish headings from paragraphs and lists. 
> 
> Write the recursive rendering logic cleanly. Keep performance in mind, as medical documents can be lengthy.

## Prompt 3: Selection Logic and the Floating Action Button (FAB)
**Goal:** Capture user highlights cleanly (restricted to single blocks for the MVP) and trigger the question generation UI.

**Prompt to copy/paste:**
> We need to implement the text selection engine inside the Reader View. We are restricting text selection to a *single block* at a time for this MVP to avoid cross-node selection complexity.
> 
> Task:
> 1. Implement a `useTextSelection` hook or component wrapper that listens for the `mouseup` event within the `<DocumentRenderer>`.
> 2. When text is highlighted, extract:
>    - The `data-block-id` of the parent container.
>    - The `start_offset` and `end_offset` of the selection.
>    - The exact text string selected.
> 3. If a valid selection is made within a single block, render a Floating Action Button (FAB) popover positioned just above the selected text.
> 4. The FAB should contain three small buttons for question types: "T/F", "MCQ", and "Fill-in". 
> 5. When a FAB button is clicked, dispatch a mock function `generateQuestion(blockId, text, type)` and clear the selection. 
> 
> Please provide the logic for capturing the offsets securely and positioning the absolute FAB relative to the user's selection bounding client rect.

## Prompt 4: Extensible Question Registry & UI Cards
**Goal:** Build the right-hand Review Queue using a Strategy Pattern for React components, mapping seamlessly to the Django backend's design.

**Prompt to copy/paste:**
> The right panel contains the real-time Review Queue. The backend follows an Open-Closed Strategy Pattern for question types, and the frontend must mirror this.
> 
> Task:
> 1. Create a dynamic `<QuestionRenderer>` component. It should take a `question` object `{ id, type, payload, status }` and dynamically resolve the correct UI component based on `type`.
> 2. Create a component registry (e.g., a mapping object) that maps:
>    - `'true_false'` -> `<TrueFalseCard />`
>    - `'mcq'` -> `<MultipleChoiceCard />`
>    - `'fill_in'` -> `<FillInTheGapCard />`
> 3. Implement the UI for `<MultipleChoiceCard>`. It should read `payload.options` and render selectable radio alternatives. Include a "Check" (approve) and "Close" (reject) button on the card.
> 4. Implement the UI for `<FillInTheGapCard>`. It should parse a string with tokens like `{{gap_0}}` and render inline empty slots, alongside a draggable or clickable "Word Bank" below it based on `payload.options`.
> 
> Keep the UI polished with Tailwind, matching a clean, card-based interface. Include hover states for the approve/reject actions.

## Prompt 5: WebSocket Integration and Queue Throttling
**Goal:** Connect the UI to the background task workers (Celery) via Django Channels.

**Prompt to copy/paste:**
> The final step is connecting our real-time generation loop. When the user clicks the FAB, a Celery worker generates the question and pushes it to the client via WebSockets.
> 
> Task:
> 1. Write a custom hook `useQuestionWebSocket(documentId)` that establishes a WebSocket connection to `ws://localhost:8000/ws/document/{documentId}/`.
> 2. When a `question_generated` event is received over the socket, append the new question to the `pendingQuestions` array in the Zustand store.
> 3. Implement the Queue Throttling rule: If `queueCount` (pending unapproved questions) reaches 20, visually disable the FAB in the Reader View and show a small toast/banner prompting the user to "Review pending questions before generating more."
> 4. Wire up the Approve/Reject buttons on the Question Cards to send an HTTP PATCH request to the backend updating the question status, and subsequently remove them from the pending queue in the Zustand store.
> 
> Provide the robust WebSocket hook handling reconnection logic, and show how it integrates with the Zustand store.
